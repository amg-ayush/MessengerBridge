# MessengerBridge — локальный мост Telegram ↔ MAX

.NET 10 Worker Service для Windows 11. Дублирует новые текстовые сообщения
между двумя группами от имени ботов, добавляя имя автора и источник:

```text
[Telegram] Amgalan Ayush
Виски и Пепси
```

| Настройка | Значение |
|---|---|
| Telegram Chat ID | `-5369085414` |
| MAX Chat ID | `-80442349966802` |
| Telegram API | через `http://127.0.0.1:10808` |
| MAX API | напрямую, `https://platform-api2.max.ru` |
| Получение событий | Long Polling, независимо для каждого мессенджера |
| Состояние и очередь | SQLite, создаётся автоматически |

## Быстрый запуск на Windows 11

1. Установи .NET 10 SDK, распакуй проект, открой PowerShell в папке с этим README.
   Проверка: `dotnet --version`. Открывать решение можно через `MessengerBridge.sln`.
2. Запусти v2rayN с HTTP-прокси на `127.0.0.1:10808`.
3. Исправь доверие к сертификату MAX по разделу ниже. В коде TLS-проверка включена.
4. Сохрани действующие токены ботов локально:

   ```powershell
   .\Set-BridgeSecrets.ps1
   ```

   Скрипт запросит оба токена скрытым вводом. Они передаются Secret Manager через stdin,
   не попадают в командную строку, историю PowerShell или исходники.
   Если прежний Telegram-токен ещё не отозван, сначала перевыпусти его через BotFather.
   Новый токен в переписку отправлять не нужно.

5. Проверь подключения без чтения событий и без отправки сообщений:

   ```powershell
   .\Start-Bridge.ps1 -Check
   ```

   Ожидается две строки `Telegram: OK` и `MAX: OK`.
   Проверяются токены, тип группы, администраторские права и отсутствие Webhook.
   Для MAX также проверяется `read_all_messages`.

6. Запусти мост:

   ```powershell
   .\Start-Bridge.ps1
   ```

7. Напиши новое текстовое сообщение от своего аккаунта в Telegram-группе,
   затем другое сообщение в MAX-группе. Каждое должно появиться в другой группе
   от имени бота с префиксом источника и именем автора. Остановка — `Ctrl+C`.

Компьютер, приложение и прокси должны работать. Сон/выключение Windows прерывает
синхронизацию; полную историю переписки после длительного простоя API не гарантируют.
Старые сообщения из истории групп мост не выгружает.

Если Windows блокирует скачанные скрипты, разблокируй именно эти два файла через
свойства файла → «Разблокировать» либо `Unblock-File` после просмотра содержимого.
Проверку и запуск также можно выполнить напрямую:

```powershell
dotnet run --project .\src\MessengerBridge -c Release -- --check
dotnet run --project .\src\MessengerBridge -c Release
```

## Сертификат MAX

В прежних проверках Windows возвращала `SEC_E_UNTRUSTED_ROOT` и напрямую, и через
прокси. Это нужно исправить до проверки подключения.

Официальная документация MAX указывает, что для `platform-api2.max.ru` требуется
доверие к сертификатам Минцифры. Скачай сертификаты по официальной инструкции для
Windows на <https://www.gosuslugi.ru/crt> и проверь их происхождение перед импортом.
Следуй инструкции портала: корневой сертификат относится к доверенным корневым
центрам, выпускающий — к промежуточным. Для локального запуска используй хранилище
того пользователя Windows, от которого запускается мост.

Проверка TLS без токена:

```powershell
curl.exe --noproxy "*" -i https://platform-api2.max.ru/me
```

HTTP-ошибка авторизации без токена допустима; ошибка доверия сертификату должна
исчезнуть. Затем повтори `Start-Bridge.ps1 -Check`. Если TLS всё ещё не проходит,
проверь полученную цепочку сертификатов и её издателя. В проекте нет `-k`,
`DangerousAcceptAnyServerCertificateValidator` или автоматического импорта сертификатов.

## Настройки и секреты

Основные настройки: `src/MessengerBridge/appsettings.json`. Токены в нём пустые.
После изменения перезапусти приложение. При `dotnet run` файл копируется рядом
со сборкой. Прокси задаётся отдельно для каждого мессенджера:

```json
{
  "Bridge": {
    "Telegram": { "ProxyUrl": "http://127.0.0.1:10808" },
    "Max": { "ProxyUrl": "" }
  }
}
```

Пустой `ProxyUrl` означает прямое подключение, включая игнорирование системного
прокси и `HTTP_PROXY`/`HTTPS_PROXY`. При необходимости укажи `socks5://...`.

Порядок переопределения: appsettings → User Secrets → переменные окружения.
User Secrets загружаются также для Release и Production. Значения локальны для
пользователя Windows и хранятся вне проекта; Secret Manager не шифрует их.
Альтернативно в Visual Studio: проект → «Управление секретами пользователя»:

```json
{
  "Bridge:Telegram:Token": "YOUR_NEW_TELEGRAM_TOKEN",
  "Bridge:Max:Token": "YOUR_MAX_TOKEN"
}
```

Имена переменных окружения для будущего развёртывания:

```text
Bridge__Telegram__Token
Bridge__Max__Token
Bridge__Telegram__ChatId
Bridge__Max__ChatId
Bridge__Telegram__ProxyUrl
Bridge__Max__ProxyUrl
Bridge__DatabasePath
```

`ChatId` и курсоры хранятся как `long` / SQLite INTEGER. 32-битного `int` недостаточно.

## Первый запуск и курсоры

Telegram получает ожидающие подтверждения события, которые ещё доступны API.
MAX без сохранённого `marker` отдаёт последнее обновление. Поэтому после старта
проверяй мост **новыми** сообщениями. Значение `83040` из прежней ручной проверки
не зашито в код: оно уже может быть устаревшим.

Если нужен конкретный свежий стартовый MAX marker, задай `Bridge:InitialMaxMarker`.
Он используется только при отсутствии сохранённого MAX-курсора. После каждого
успешного чтения приложение использует значение из SQLite.

Не запускай другой `getUpdates`/`GET /updates` параллельно с мостом: другой
потребитель может подтвердить события раньше него. На одного бота — один poller.
Приложение блокирует одновременный запуск с той же БД, но не может обнаружить
другой компьютер или экземпляр с отдельной БД.

## Очередь и восстановление

Полученные сообщения и следующий курсор сохраняются **одной транзакцией**.
Только после этого poller делает следующий запрос с подтверждением прочитанного.
Отправка работает отдельно в каждом направлении: недоступность получателя
не мешает сохранять доступные входящие сообщения. Повторно полученное сообщение
не создаёт вторую запись благодаря уникальному ключу источника/чата/сообщения/части.

Сеть, HTTP 429 и 5xx повторяются с увеличивающейся задержкой; учитывается
`retry_after` и HTTP `Retry-After`. Пока отправка первой части отложена, следующие
сообщения этого направления ждут. Ошибка 4xx, кроме временных кодов, сохраняется
как `failed`, после чего очередь может продолжить отправку следующих сообщений.
После исправления причины можно явно вернуть такие записи в очередь.
Сопоставление исходного и отправленного ID хранится в `outbox.target_message_id`.

Отправка ограничена одной частью примерно в 3,1 секунды на направление. Это
консервативный режим для групп Telegram; при всплеске сообщений растёт очередь.
Текст делится на части до 3500 UTF-16 code units, без разрыва surrogate pair.
Каждая часть содержит заголовок автора. HTML/Markdown-разметка не включается.

**Гарантии доставки:** автоматические повторы возможны. Если API принял сообщение,
но ответ потерялся, или процесс остановился между отправкой и записью `sent`,
после восстановления может появиться дубль. Атомарной транзакции между SQLite и
API мессенджера нет; exactly-once этот мост не обещает.

По умолчанию БД находится относительно каталога сборки:
`src/MessengerBridge/bin/Release/net10.0/data/bridge.db` при запуске скриптом.
Полный путь выводится при старте. Чтобы состояние не зависело от Debug/Release
или публикации, рекомендуется один раз задать постоянный абсолютный путь:

```powershell
dotnet user-secrets set "Bridge:DatabasePath" "C:\Projects\MessengerBridge\data\bridge.db" --project .\src\MessengerBridge
```

Папка создастся автоматически. БД содержит текст переписки и сохранённые сообщения;
она не зашифрована. Очередь и история ID в первой версии автоматически не очищаются.
Для резервной копии останови мост и скопируй всю папку с БД. Не удаляй БД для
обычного перезапуска — в ней курсоры, очередь и сведения об уже отправленном.

Команды обслуживания выполняются при остановленном мосте:

```powershell
.\Start-Bridge.ps1 -Status
.\Start-Bridge.ps1 -RetryFailed
```

`-Status` показывает счётчики и курсоры без текста сообщений. `-RetryFailed`
переочередит все `failed` и обновит их адресата по текущим Chat ID в конфигурации.
Обычный запуск затем выполнит отправку. Эти две команды не требуют токенов.

Если Telegram преобразовал группу в supergroup, приложение сообщит новый Chat ID.
Обнови `Bridge:Telegram:ChatId`, выполни проверку, затем `-RetryFailed` и запуск.
У уже ожидающих записей адресат сохранён на момент получения; записи со старым ID
могут сначала перейти в `failed`, после чего их нужно переочередить той же командой.

## Что входит в первую версию

- Новые текстовые сообщения пользователей из двух заданных групп, в обе стороны.
- Имя автора и метка источника.
- SQLite outbox, курсоры, повторные попытки, соответствия ID и проверка подключения.
- Игнорирование ботов в обеих платформах для защиты от циклической пересылки.
- Пропуск анонимных администраторов и сообщений от имени каналов в Telegram.
- Журналы без токенов, полных URL Telegram, имён участников и текста сообщений.

Фото, видео, файлы, голосовые, стикеры, подписи вложений, реакции, редактирование,
удаление и связи ответов пока не синхронизируются. Это первая версия текстового моста.
Сообщения отправляются от имени ботов; имя участника добавляется в текст.

## Проверки и сборка

```powershell
dotnet test .\MessengerBridge.sln -c Release
dotnet publish .\src\MessengerBridge -c Release -r win-x64 --self-contained false -o .\publish\win-x64
```

После публикации запускай `publish/win-x64/MessengerBridge.exe`. Нужен .NET 10
Runtime на Windows. Если абсолютный путь БД не задан, каталог `data` будет рядом
с EXE: при переходе со сборки на опубликованную версию перенеси состояние туда
или задай один и тот же абсолютный путь. Останови прежнюю копию перед запуском.
Проверка опубликованной версии: `MessengerBridge.exe --check`.

## Перенос на нидерландский VPS

Исходники не привязаны к Windows; на Linux можно собрать тот же worker. Для
постоянной работы потребуется добавить Webhook: MAX официально допускает polling
для разработки/тестирования и требует Webhook для production. В этой версии
Webhook endpoint ещё нет. После добавления его обработчик сможет писать в ту же
SQLite-очередь; механизм отправки можно сохранить.

При переносе останови Windows-копию, перенеси SQLite и задай токены на сервере
через окружение. Проверь доверие к цепочке MAX уже на Linux. Прокси Telegram можно
очистить, если API доступен с VPS напрямую. Само размещение в Нидерландах не
заменяет проверку фактической доступности обоих API.
